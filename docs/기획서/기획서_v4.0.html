§1

이 문서가 v3.0과 다른 점

v3.0은 읽고 나면 구현이 시작되는 문서였다. 이번은 아니다. 세 방향에 합의하는 것까지가 이 문서의 역할이고, 그 아래는 각자 파고든다.

항목v3.0v4.0
문서의 역할 설계까지 확정 — 테이블·화면·제한시간이 전부 적혀 있었다 방향만 확정 — 무엇을 만들지만 적고 어떻게는 각자 정한다
분량 8절 · 미결정 7건 5절 · 열린 질문은 목표마다 하나씩
전제 만들면서 알게 된 것 발표를 받고 정한 것 — 목표 3은 중간발표 피드백에서 나왔다
왜 얇게 쓰는가

v3.0을 두껍게 쓴 이유는 네 명이 병렬로 일하려면 계약이 먼저 필요했기 때문이다. 지금은 계약(@zeteo/shared-types)이 안정돼 있고 각자 자기 파트를 안다. 이 시점에 세부 설계를 문서로 먼저 못 박으면 실제로 짜면서 알게 될 것을 추측으로 미리 굳히게 된다. 결론은 여기 남기고, 과정은 코드와 -logs에 남긴다.

§2

목표 셋

셋 다 설계 전이다. 아래는 무엇을 만들지에 대한 합의이지 설계안이 아니다. 각 항목의 열린 질문이 그 목표에서 가장 먼저 답해야 할 것이다.

학습

쌓인 데이터로 봇이 스스로 나아지게

지금은 게임이 끝나면 기록이 DB에 들어가고 거기서 멈춘다. 조회해서 무엇이 문제였는지 판단하고, 그것을 다음 판의 봇에 되먹이는 고리를 닫는다.

경계적재까지 유민성 · 조회부터 김정현
상태설계 전
열린무엇을 학습 기준으로 볼 것인가
방

번호를 치지 않고 목록에서 골라 들어가게

지금은 미리 정해둔 번호를 입력해 들어간다. 열려 있는 방이 대시보드에 보이고, 눌러서 들어간다. 제목으로 찾을 수 있고, 나갔다 다시 들어올 수 있다.

범위방 목록 화면(신규) · 서버 방 생명주기
상태설계 전
열린진행 중인 방을 목록에서 어떻게 다룰 것인가 — 잠글지, 재입장만 열지
리플레이 신규

게임이 끝난 뒤 대화를 다시 볼 수 있게

중간발표 피드백에서 나온 항목이다. 설문 화면 안에 둔다. 답을 쓰다가 대화를 다시 보고, 보다가 답으로 돌아온다. 따로 떨어진 단계가 아니라 설문과 오가는 한 자리다.

효과설문 답변의 근거가 기억에서 기록으로 바뀐다
상태설계 전
열린오갈 때 쓰던 답이 남아 있어야 하는가

화면 흐름은 그대로다

전결과  →  설문  →  랜딩
후결과  →  설문 ⇄ 리플레이  →  랜딩

리플레이는 단계가 아니라 설문 안의 자리다. 순서를 새로 정할 일이 없고, 설문을 마치면 지금처럼 랜딩으로 나간다. 답을 쓰다가 근거를 확인하러 다녀올 수 있다는 것이 이 목표의 전부다.

§3

바닥 다지기

목표 셋보다 먼저 한다. 흠이 남아 있는 코드 위에 새 구조를 얹으면, 나중에 문제가 났을 때 새로 넣은 것 탓인지 원래 있던 것 탓인지 가려낼 수 없다.

할 일담당내용
버그 수정 전원 내 파트가 아니어도 발견하면 알린다. 고친 내용은 각자 -logs에 한 줄씩 남긴다 — 같은 것을 두 사람이 고치는 일을 막기 위함이다
주석 각자 소유 파일 무엇을 하는지가 아니라 왜 그렇게 했는지를 적는다. 코드를 읽으면 알 수 있는 것은 안 적는다
최적화 각자 소유 파일 측정한 것만 손댄다. 느리다고 느낀 것과 실제로 느린 것은 다르다
먼저 정리할 것

feat/server의 0b453ea “DB <-> BOT”(knowledge.ts · history.ts — 과거 설문 사유를 봇 프롬프트에 자동으로 넣는 코드)가 dev 병합에서 빠진 채로 남아 있다. 사람이 확인하지 않은 내용이 프롬프트에 바로 들어가는 방식이라 뺐던 것인데, 목표 1과 정면으로 겹친다. 목표 1을 시작하기 전에 두 사람이 먼저 맞춘다.

§5

이 문서가 정하지 않는 것

아래는 일부러 비워둔 자리다. 빠뜨린 것이 아니다.

  • 학습 신호의 구체적인 형태 — 설문만 볼지, 관전자 봇 지적까지 볼지, 어떤 쿼리를 열지. 데이터를 실제로 꺼내 봐야 정해진다
  • 방 목록에 무엇을 띄울지 — 제목 · 인원 · 진행 상태 중 어디까지 보여줄지, 인원 규칙을 방마다 다르게 둘지
  • 리플레이의 표시 방식 — 로그를 통째로 펼칠지, 흐름대로 다시 감을지
  • 화면 디자인 — 새로 생기는 화면의 배치는 만드는 사람이 정한다. 토큰만 지키면 된다
잠글 것이 생기면

각자 파고들다가 다른 파트가 맞춰야 하는 값이 나오면 — 타입이든 이벤트 이름이든 — 그때 @zeteo/shared-types에 올린다. 직접 고치지 않고 알린다. 하루에 세 사람이 같은 필드를 각자 추가한 일이 실제로 있었다.
