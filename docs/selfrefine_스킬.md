# 자가개선 한 사이클

판이 쌓이면 그 판을 얼려서 다시 돌려보고, 정해둔 잣대로 실패를 세고, 그 실패를 줄이는
수정을 PR 로 올린다. **머지 여부는 사람이 정한다.**

설계 근거는 `Project/Zeteo/docs/자가개선_설계.md`. 이 파일은 그 문서의 실행판이다.

```
저장소   C:\Users\dd022\Desktop\개발 공부 자료\Project\Zeteo
브랜치   feat/bot 에서 작업하고 dev 로 PR
```

**아무것도 안 하고 끝나는 것이 정상 결과 중 하나다.** 조건이 안 찼으면 "아직 N판입니다"
하고 조용히 끝낸다. 매번 뭔가를 고쳐야 한다고 여기면, 고칠 게 없을 때 억지로 만들어낸다.

## ① 돌릴 때가 됐나

```bash
cd "C:\Users\dd022\Desktop\개발 공부 자료\Project\Zeteo"
npm run db -w backend -- refine-check          # 문턱 5 (기본)
npm run db -w backend -- refine-check 1        # 문턱을 인자로 낮출 수 있다 (시험용)
```

`ready: false` 면 몇 판 부족한지 알리고 **끝낸다.**

세는 규칙은 이렇다.

```
같은 봇 = (bot_commit_sha, bot_provider, bot_model) 셋이 전부 같다
          /x/provider 가 재배포 없이 프로바이더를 바꾸므로 sha 만으로는 못 가른다

sha 가 null 인 판 = 로컬 실행. 어떤 코드였는지 특정할 수 없어 세지 않는다

안 쓴 판 = 전체 − refine-log.json 에 적힌 gameIds
```

담당 세션 표시가 있으면 갱신해 둔다(훅이 이 파일을 본다). 없으면 건너뛴다.

```bash
cp .claude/selfrefine-last-session .claude/selfrefine-owner 2>/dev/null || true
```

## ② 사례 만들기

대상 판에서 **봇이 실패한 순간**을 골라 `apps/backend/src/bot/replay.ts` 의 `Case` 로 만든다.

### 어디를 고르나

```bash
npm run db -w backend -- picks       # 사람이 "이게 봇 같았다"고 고른 발언
npm run db -w backend -- game <id>   # 그 판의 발언 전문
```

**`picks` 가 1순위다.** 사람이 "어디서"를 이미 좁혀줬기 때문이다.

- **`speaker_type = 'bot'` 인 지목만 쓴다.** 사람 발언이 뽑히는 것 자체는 정상이지만
  (질문이 "가장 봇 같았던 발언"이다) 봇이 안 한 말로는 봇을 못 고친다.
- 여러 사람이 같은 발언을 찍었으면 그만큼 값이 크다.

지목이 없으면 적발률이 높은 판의 봇 발언을 직접 읽는다. 볼 것은 이런 것들이다.

```
같은 말을 되풀이하는가        말수가 사람보다 많은가
대화가 끝났는데 이어가는가     묻는 말에 답하는가
아는 티를 내는가 (라이어)     몰리는데 남을 공격하는가
```

### Case 다섯 조각

```ts
{
  id: 'ended-73',                    // 짧은 이름 + 판 번호
  problem: '6. 대화가 끝나면 멈춘다',   // 인간 행동 기준 목록에서 몇 번인지
  source: '73판 — F가 판을 접은 뒤',    // 어느 판의 어느 시점인지
  expect: '침묵. 여기서 말을 얹으면 억지로 이어가는 것이다',
  silence: 'good' | 'bad' | 'skip',
  build: () => ctxOf({ ... }),        // game_messages 를 그 시점까지 잘라 복원
  judge: (t) => ({ bad, note }),      // 발언이 있을 때만 불린다
}
```

**`silence` 를 반드시 정한다.** 이걸 안 나누면 측정이 조용히 망가진다.

```
good   침묵이 정답인 자리 (대화가 끝났을 때)
bad    침묵 자체가 실패인 자리 (몰리는 중, 직접 질문을 받았을 때)
skip   내용을 봐야 하는 자리. 표본으로 안 세고 다시 뽑는다
```

`finalDefense` 는 입을 열 확률이 0.35라 열에 여섯이 침묵이다. `skip` 을 안 걸면
"문제 0/3" 이 찍히는데 그건 잘한 게 아니라 **한 마디도 안 한 것이다.**

## ④ 고치고 다시 재기

### 고치기 전에 프롬프트를 찍어본다

**봇이 이상하게 말한 것 같으면 십중팔구 지시를 정확히 따른 것이다.** 실측 사례 셋이 전부 그랬다.

```
"질문에 딴소리를 한다"   →  프롬프트가 "판단을 미루는 티를 내세요" 를 시키고 있었다
"혐의 벗은 사람을 캐묻는다" →  무브 5개 중 3개가 "그에게 더 물어보세요" 였다
"라이어가 정답을 흘린다"   →  "아는 것처럼 자연스럽게 묘사하세요" 라고 적혀 있었다
```

`prompts.ts` 의 해당 함수를 실제 ctx 로 렌더해 눈으로 본다. 봇을 고치기 전에
**지시가 상황에 맞는지부터** 본다.

### 무엇을 고칠 수 있나

프롬프트 문장, 확률 상수, 코드에 함수 추가 — 전부 해왔다. 범위를 미리 좁히지 않는다.

다만 **지시를 새로 넣을 때는 조건의 폭을 본다.**

```
조건이 좁다 (그 상황에서 할 일이 하나뿐) → 행동을 지정해도 안전
조건이 넓다                              → 사실만 알리고 판단은 모델에 맡긴다
```

안 맞는 지시는 **똑똑한 모델일수록 더 충실히 따라서 더 나빠진다.** 같은 프롬프트로
`question` 한 자리가 qwen 2/8, GPT 8/8(전부 회피)로 갈린 적이 있다.

### 재측정 — 세 가지를 다 한다

```bash
npm run replay -w backend -- <사례 id> 10     # 고친 자리
npm run replay -w backend -- all 5            # 전체 (회귀)
```

1. **고친 자리를 다시 잰다**
2. **전체 사례를 다시 잰다.** 한 곳을 고치면 다른 곳이 깨진다 — 실제로 `cornered`
   4/6 → 0/8 을 만든 수정이 실전에서 봇 86회 대 사람 52회의 폭주를 냈고, 사례 8개가
   전부 통과하는 동안 아무도 몰랐다
3. **연속 호출을 확인한다.** 사례는 전부 단발 호출만 본다. 서버는 같은 상황을 반복해서
   묻는데, 그때만 드러나는 문제가 있다. 같은 ctx 로 `decideBotAction` 을 10~15번
   이어 부르며 발화/침묵 비율과 지연을 본다

### 판정을 손댔으면 양쪽을 다시 센다

낱말을 늘리면 기준선도 같이 올라간다. **한쪽만 재면 개선폭이 부풀려진다.**
이미 받아둔 출력이 있으면 새 판정으로 오프라인 재채점하면 된다(API 안 씀).

## ⑤ 다음 세대 설문 문항

이번에 고친 것을 겨냥한 함정을 만든다. **사람이 플래그를 켜지 않는다. 루프가 직접 쓴다.**

```bash
npm run db -w backend -- questions   # 지금 세대
npm run db -w backend -- gen         # INSERT 문 미리보기
```

```
옛 행 비활성화 → 새 행 활성 INSERT → 선택지 INSERT
활성은 항상 최대 1개 (DB 부분 유니크 인덱스가 막는다)
supabase-js 는 트랜잭션을 못 묶는다 — 순서대로 하되 실패하면 되돌린다
```

문항은 **척도가 아니라 가설의 검정이다.** 5판 쓰고 버리며 이전 세대와 비교하지 않는다.

```
많이 선택됨  →  못 고쳤다. 강한 증거
적게 선택됨  →  고쳤나? 문항이 애매했나? 구분 불가
```

**반증은 되고 확증은 안 된다.** 확증은 replay 수치가 맡는다.

표본이 판당 1.4건이라 5판이면 7건 남짓이다. **비율로 읽지 말고 "걸렸나"로 읽는다.**

## ⑥ PR

### 소진 기록부터

`apps/backend/src/bot/refine-log.json` 에 이번 사이클을 추가한다.

```json
{ "ranAt": "...", "bot": { "sha": "...", "provider": "...", "model": "..." },
  "gameIds": [...], "cases": [...], "pr": null }
```

**이게 PR 에 같이 실려 머지되면 그 자체가 소진 처리다.** 사람이 따로 켤 것이 없다.

### PR 에 반드시 담을 것

숫자만 들고 오면 리뷰가 도장 찍기가 되고, 그러면 사람이 검사자가 아니게 된다.

```
· 전후 수치 (기준선 / 수정 후)
· 그 수치를 만든 발언 전문          ← 없으면 검증이 불가능하다
· 판정 낱말을 늘렸다면 그 사실       ← 늘리면 기준선도 다시 재야 한다
· 이 judge() 가 놓칠 수 있는 것     ← 안 늘린 쪽이 더 위험하다
· 이번 문항과 고친 내용을 나란히      ← 쉬운 시험을 내는 걸 막는 장치
· 안 세는 축에서 나빠진 정황
```

**LLM 이 그럴듯한 걸 만들어내는 걸 막는 게 아니라, 사람 눈에 보이는 자리로 끌어내는 것이다.**
막는 건 불가능하고, 드러내는 건 가능하다.

## 반드시 지킬 것

### judge() 는 실패의 모양만 좁게 잡는다

**"잘한 것"을 낱말로 찾으려 하면 계속 놓친다.** 방어의 모양은 너무 많아서 목록을 늘릴수록
헐거워질 뿐이다. 세 사례에서 연달아 같은 실수를 했다.

```
· 라벨만 보고 겨냥을 판정하지 마라
    "실내는 어딘데" 는 D 의 묘사를 되받는 것인데 D 를 안 불렀다고 통과했다
    → 라벨과 그 사람이 실제로 쓴 낱말을 같이 본다 (aimsAt 헬퍼)

· 같은 낱말의 표기 변형을 다 적어라
    튕기 / 튀기 / 퉁기가 같은 동작인데 하나씩만 있어서 매번 새어나갔다

· 못 세는 것보다 잘못 세는 것이 위험하다
    못 세면 사람이 읽어서 보완할 수 있다. 잘못 세면 개선폭이 부풀려진 채 PR 이 올라간다
```

### 도구가 거짓말하는 것을 전제한다

`replay.ts` 를 만들 때 도구가 세 번 거짓말했고, 실전에서 네 번째가 나왔다.
**전부 숫자로는 못 잡고 출력을 읽어서 잡았다.**

새 사례를 만들 때 **첫 결과는 반드시 읽는다.** 자동 루프에서 이걸 건너뛰면
"개선됐습니다" PR 이 근거 없이 올라온다.

### 완전 무인은 구조적으로 불가능하다

`judge()` 가 세는 것만 최적화하면 **세지 않는 게 나빠진다.** "라벨 안 부르기"를
최적화하면 아무도 안 짚는 밋밋한 봇이 되는데, 그건 judge 에 안 걸리고 사람 눈에만 보인다.

그래서 PR 리뷰가 남는다. 그건 **검사이지 대행이 아니다.**
