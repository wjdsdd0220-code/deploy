# 자가개선 루프 — 설계 인계 (2026-08-24)

> 봇 세션에 넘기는 문서. 이 대화는 **설계**만 했고 코드는 한 줄도 안 건드렸다.
> 구현은 봇 세션이 한다. `파트B_인수인계.md` 와 짝이다.

---

## §0. 한 문장

**판이 5개 쌓이면 그 판을 얼려서 다시 돌려보고, 정해둔 잣대로 실패를 세고,
그 실패를 줄이는 프롬프트 수정을 PR로 올린다. 머지 여부는 사람이 정한다.**

용어로는 **HITL Self-Refinement** 인데, 보통 쓰이는 뜻과 다른 점이 하나 있다.

```
흔한 self-refinement   한 번의 응답을 그 자리에서 고친다 (초안 → 자가비평 → 재작성)
이 설계                여러 판을 모아 봇의 규칙 자체를 고친다
                       주기 = 5판,  산출물 = 코드 diff
```

고쳐지는 게 **발언이 아니라 프롬프트**다. 그래서 PR이 나온다.

### 관전자 봇은 어디 갔나

기획서 v3.0 §3-1의 관전자 봇이 **암묵적으로 들어가 있다.** 런타임 컴포넌트가
아니라 오프라인 도구 안으로 옮겨간 형태다.

| | v3.0 관전자 봇 | 이 설계 |
|---|---|---|
| 어디서 도나 | 서버, 판 끝날 때마다 | 오프라인, 조건 충족 시 |
| 산출물 | DB 행 (발언별 지적) | **코드 diff** |
| 검증 | 그 LLM을 믿어야 함 | **replay 전후 비교로 검증 가능** |
| 게임 영향 | 있음 | 없음 |

8/12에 민성님 `knowledge.ts`(설문 사유 자동 주입)를 반려한 이유가
*"사람 확인 없이 프롬프트에 바로 들어간다"* 였는데, **이 설계는 PR이 그 확인
지점**이라 원칙과 충돌하지 않는다.

## §0-1. 설계 원칙 — 사람은 검사자지 대행자가 아니다

> **사람이 하는 일은 "봇이 이상한 결론을 냈는지 검사하는 것" 하나뿐이다.
> 봇이 못 하는 일을 사람이 대신하는 단계는 만들지 않는다.**

이 원칙이 여러 선택을 이미 갈랐다.

```
문항 전환    "머지 후에 사람이 플래그를 켠다" 를 버리고 루프가 직접 쓰게 함 (§3 ⑤)
PR 승인      이건 남긴다 — 검사이지 대행이 아니다
```

판단 기준은 이렇다. **그 단계가 없으면 봇이 틀린 채로 굴러가는가**(→ 남긴다),
아니면 **봇이 할 수 있는데 손이 안 닿아서 사람이 하는가**(→ 없앤다).

## §1. 실측 — 설계의 근거

2026-08-24 기준. 추측이 아니라 DB를 직접 센 값이다.

```
                        08-24   08-26
games                      41      42
game_messages            1141    1147
survey_responses           49      52
survey_response_reasons    54      58

종료된 판              34
설문이 1건 이상인 판    19   ← 44%의 판이 설문 0건
사람 전원이 낸 판       11   ← 32%
자유서술이 있는 응답     14 / 49  (29%)
봇 적발률               39 / 59 = 66%
발언 지목               3    ← 08-26 부터 쌓이기 시작
```

비율은 08-24 실측이다. 판이 하나 늘어난 정도라 결론은 그대로 유효하다.

**판의 절반 가까이가 설문을 통째로 못 건진다.** 설문 기반 설계는 데이터의
절반을 버리고 시작한다는 뜻이다.

### 데이터 3층

```
A 무조건 남는 것   game_messages 전량 · game_votes
                   games.bot_detected_count / bot_voter_total
                   유실 0%. 사람 행동과 무관하다

B 거의 남는 것     봇 지목 (누가 누구를)
                   botVote 20초를 놓치면 유실

C 자주 비는 것     설문 사유 · 자유서술
                   56% / 71% 유실
```

**A만으로 학습이 굴러가야 한다.** 적발률이 이미 결과 라벨이고 봇 발언이 전부
남아 있으니 *"들킨 판 vs 안 들킨 판의 봇 발언 비교"* 가 된다. C는 있으면 훨씬
좋은 재료지 전제가 아니다.

> 자유서술 한 줄이 체크박스 49건보다 값이 컸던 실적이 있다 — `0028` 판의
> *"너무 명확한 정보를 알고있다"* 가 라이어 유출 버그를 통째로 찾아냈다.

## §3. 만들 것 — `/selfrefine`

```
① 돌릴 때가 됐나 검사
   "이 봇으로 끝난 판이 5개인가" 가 아니라 **"아직 안 쓴 판이 5개인가"** 다
   아니면 조용히 끝낸다   ← SHA 만 보면 틀린다. §9 / 소진 표시는 §10

② DB → 사례
   그 판들에서 실패 지점을 뽑아 replay.ts Case 로 만든다
   (지금은 4판이 손으로 박혀 있다)

③ 잣대 적용
   judge() 로 기준선 측정

④ 수정 + 재측정
   수정 → 같은 자리 다시 측정

⑤ 다음 세대 설문 문항 작성 — 루프가 DB 에 직접 쓴다
   survey_questions 에 새 행을 활성으로 INSERT + 옛 행 비활성화 (한 트랜잭션)
   활성 행은 항상 최대 1개라 둘을 따로 하면 인덱스에 걸린다
   사람이 켜는 단계는 두지 않는다 (§0-1)

⑥ PR
```

### ①을 먼저 두는 이유

**트리거를 완벽하게 만들 필요를 없애려는 것이다.** 아무 데서나 눌러도 안전하면
훅이 조잡해도 되고, 사람이 가끔 쳐도 된다.

**아무것도 안 하고 끝나는 것이 정상 결과 중 하나다.** 조건이 안 찼으면
"아직 N판입니다" 하고 조용히 끝낸다. 매번 뭔가를 고쳐야 한다고 두면, 고칠 게
없을 때 억지로 만들어내게 된다.

### 자동화 범위 — 미정. 봇 코드를 아는 쪽이 정한다

**이 문서는 여기에 선을 긋지 않는다.** 지금까지의 수정 이력이 그럴 근거를 주지
않기 때문이다 — replay 실측으로 문제를 찾아 **코드에 함수를 새로 만든 적도,
프롬프트 문장을 고친 적도** 있고, 오히려 확률 상수를 건드린 쪽이 적었다.

그러니 *"상수만 만지게 한다"* 같은 제한은 실제로 해온 일과 어긋난다.

열어두는 질문:

```
· 어떤 수정까지 사람 확인 없이 만들어도 되는가
· 그중 replay 로 전후를 잴 수 있는 것은 어디까지인가
· 되돌리기 비용이 큰 수정이 따로 있는가
```

### 상한이 있다면 judge() 의 표현력이다

`replay.ts` 머리 주석이 이미 못 박아뒀다.

> 판정은 기계가 확실히 셀 수 있는 것만 본다. **눈치가 있는지 없는지는 셀 수
> 없으므로 발언을 전부 찍어 사람이 읽게 둔다.**

**judge() 가 세는 것만 최적화하면 세지 않는 게 나빠진다.** *"라벨 안 부르기"* 를
최적화하면 아무도 안 짚는 밋밋한 봇이 되는데, 그건 judge() 에 안 걸리고 사람
눈에만 보인다. 그래서 **완전 무인은 구조적으로 불가능하다.**

### PR에 반드시 담을 것

숫자만 들고 오면 리뷰가 도장 찍기가 되고, 그러면 HITL의 H가 사라진다.

```
· 전후 수치 (기준선 / 수정 후)
· 그 수치를 만든 발언 전문          ← 없으면 검증 불가
· 판정 낱말을 늘렸다면 그 사실       ← 늘리면 기준선도 다시 재야 한다
· 이번 문항과 고친 내용을 나란히      ← 봇이 쉬운 시험을 내는 걸 막는 장치
· 안 세는 축에서 나빠진 정황
```

**LLM이 그럴듯한 걸 만들어내는 걸 막는 게 아니라, 사람 눈에 보이는 자리로
끌어내는 것이다.** 막는 건 불가능하고, 드러내는 건 가능하다.

### 측정 도구를 의심할 것

`replay.ts` 만들 때 **도구가 세 번 거짓말했다.**

```
· 침묵을 통과로 셈 — finalDefense 는 열에 여섯이 침묵이라 "문제 0/3"이 찍혔다
· 라벨만 보고 겨냥 판정 — "실내는 어딘데"가 D의 묘사를 되받는 것인데 통과했다
· 표기 변형 — 튕기 / 튀기 / 퉁기가 같은 동작인데 목록에 하나씩만 있었다
```

**전부 숫자로는 못 잡고 출력을 읽어서 잡았다.** 자동 루프가 이걸 놓치면
개선폭이 부풀려진 채로 PR이 올라온다 — 실제로 `4/10 → 실제로는 6/9` 였던 일이 있다.

## §4. 트리거 — 웹훅이 막힌 이유

디스코드 웹훅으로 봇을 태그해 스킬을 부르는 안을 검토했고, **구조적으로
불가능**해서 폐기했다.

`~/.claude/plugins/cache/claude-plugins-official/discord/0.0.4/server.ts`

```ts
813  process.stderr.write(`... bot=${msg.author.bot} ...`)
814  if (msg.author.bot) return          ← 여기서 끝
815  handleInbound(msg)                  ← gate() 는 이 안에 있다
```

디스코드에서 **웹훅 메시지는 `author.bot = true`** 로 온다. 플러그인이 고른 게
아니라 API가 그렇게 준다. 채널을 새로 파도, 멘션을 붙여도 **`gate()` 까지 도달을
못 한다.**

> 검증법 — 813번 줄이 이미 `bot=` 을 stderr 에 찍는다. 웹훅으로 한 번 쏘고
> 플러그인 로그를 보면 `bot=true` 가 보인다.

**밀린 메시지도 안 따라잡는다.** 전달 경로가 `messageCreate → gate() → mcp.notification()`
인데 큐가 없고, `ready` 에서 과거 메시지를 훑지도 않는다. `inbox/` 는 첨부파일
저장소지 메시지 큐가 아니다. **세션이 꺼져 있는 동안 온 메시지는 사라진다.**

### 그래서 훅 — 원리와 결정

훅은 **클로드 코드가 정해진 순간마다 셸 명령을 실행해 주는 것**이다. 클로드가
판단해서 부르는 게 아니라 이벤트가 나면 무조건 돈다.

```
클로드 코드 ──stdin 으로 JSON──▶  스크립트
                                    │
            ◀──종료코드 + stdout────┘
```

들어오는 JSON 에 `cwd`(지금 폴더)와 `stop_hook_active`(뒤에서 다룸)가 있다.
종료코드는 `0` 조용히 끝 / `2` 막고 stderr 를 클로드에 전달 / 그 외 에러지만 진행.

**`Stop` 과 `UserPromptSubmit` 은 매 턴 돈다.** 세션 시작 때만이 아니다.

```
세션이 꺼져 있었다  →  다시 켤 때 첫 턴에서 걸림
계속 켜두고 있다    →  Stop 이 응답 끝날 때마다 확인
```

바로 이 성질 때문에 §10 의 소진 표시가 필요하다 — 하루에 수십 번 물어보는데
개수를 세는 조건은 물어볼 때마다 같은 답을 준다.

#### 훅이 루프를 돌리는 게 아니다 — 클로드를 붙잡을 뿐이다

`Stop` 훅이 stdout 으로 이걸 뱉으면 클로드가 **답변을 끝내려다 말고 이어서 일한다.**

```json
{ "decision": "block", "reason": "안 쓴 판이 5개 모였다. /selfrefine 을 실행해라." }
```

훅은 셸이라 판단은 해도 프롬프트를 고칠 수 없으므로, **감지는 훅이 / 작업은 세션이**
맡는 형태다. 사용자가 아무 말도 안 해도 시작된다.

```
정현   "이 함수 고쳐줘"
클로드  다 됐습니다.
             ▼ Stop 훅 → 안 쓴 판 5개? → block
클로드  (안 끝나고) 자가개선 루프를 시작합니다...
```

#### 무한루프 방지

`/selfrefine` 이 끝나도 그건 또 답변 끝이라 `Stop` 이 다시 돈다. 그래서 stdin JSON 의
**`stop_hook_active`** 를 스크립트 맨 앞에서 보고 `true` 면 즉시 나간다.

단 이건 **한 답변 안에서 두 번 도는 것만** 막는다. 다음 세션에선 `false` 로 돌아오므로
§10 의 소진 표시를 대신하지 못한다.

#### 어디에 둘 것인가 — 결정: `Zeteo/.claude/settings.local.json`

| 위치 | 영향 범위 |
|---|---|
| `~/.claude/settings.json` | 정현의 **모든 프로젝트** (지금 Orca 훅 10개가 여기 있다) |
| `Zeteo/.claude/settings.json` | **깃에 올라감** → 팀원 전원 컴퓨터에서 돎 |
| **`Zeteo/.claude/settings.local.json`** | **정현의 Zeteo 에서만. 이걸로 간다** |

자가개선은 봇 담당 혼자 도는 게 맞다. 팀 저장소에 올리면 민성이 서버를 고치다가
갑자기 봇 프롬프트 PR 이 열린다.

#### 이미 확인된 환경

`~/.claude/settings.json` 의 Orca 훅 10개는 Orca 가 자동 설치한 것이고, 하는 일은
stdin 을 로컬 서버(`127.0.0.1:<포트>/hook/claude`)로 POST 하는 알림 파이프뿐이다.
**항상 `exit 0`** 이라 판단에 끼어들지 않는다. 같은 이벤트에 훅을 더 붙여도 나란히 돈다.

거기서 공짜로 확인된 것 하나 — 등록된 명령이 `if [ -f ... ]; then` 형태다.
**이 윈도우에서 훅이 POSIX 셸로 실행된다는 뜻이라, 새 훅도 bash 로 쓰면 된다.**

#### 주의

```
· Stop 은 매 턴 도니 여기서 매번 Supabase 를 때리면 안 된다.
  싼 검사로 먼저 거르고 통과할 때만 DB 를 본다 (기본 타임아웃 60초 동안 턴 종료가 막힌다)
· 훅 설정은 세션 시작 시점에 스냅샷된다 — 고치면 세션을 새로 켜야 먹는다
· 지금 걸린 훅은 /hooks 로 확인
```

## §5. 설문 함정 — 쓰는 법과 위험

### 무엇인가

```
봇의 A 문제를 고쳤다
   → 다음 5판 문항을 "A가 드러났는가?" 로 채운다
   → 많이 선택되면 제대로 안 고쳐진 것
   → 5판 뒤엔 버린다. 이전 세대와 비교하지 않는다
```

문항이 척도가 아니라 **가설의 검정**이다.

### 위험 1 — 표본이 아주 적다

```
34판 → 설문 49건 = 판당 1.4건
5판  → 약 7건
```

**7건짜리 비율은 신호가 아니다.** 3/7이 나와도 우연과 구분이 안 된다.

→ **비율로 읽지 말고 "걸렸나" 로 읽는다.** 한 명이라도 찍었으면 그 판을 연다.

### 위험 2 — 한쪽으로만 유효하다

```
많이 선택됨  →  못 고쳤다.  강한 증거
적게 선택됨  →  고쳤나?  문항이 애매했나?  아무도 못 느꼈나?   구분 불가
```

**반증은 되고 확증은 안 된다.** replay 수치가 확증 담당, 함정이 반증 담당이다.

### 위험 3 — 봇이 쉬운 시험을 낼 수 있다 🔴

지표를 최적화하는 게 아니라 **지표를 스스로 출제**하는 구조다.

```
고친 것   라이어가 너무 정확하게 묘사하는 문제
문항      "봇의 말투가 어색했다"        ← 아무도 안 찍음 → "해결됐네"
```

**거짓말할 의도가 없어도 이렇게 된다.** 애매한 문항은 자연히 선택률이 낮다.

→ **막는 법은 하나다. PR에 고친 내용과 문항을 나란히 올려 리뷰어가 짝이 맞는지
보게 하는 것.**

수십 개인데 전부 사례로 만들 수는 없다.

**전제는 갖춰졌다 (2026-08-26).** 발언 지목이 끝까지 연결돼 실제로 쌓이기
시작했으므로(3건), 사람이 지목한 발언을 사례 후보로 쓸 수 있다.

여기서 §0-1 과 긴장이 있다. *"첫 사이클은 사람이 고른다"* 는 봇이 못 하는 걸
사람이 대신하는 모양이다. 표본 3건이면 정말 못 하는 것인지, 아니면 손이 안 닿는
것뿐인지 **봇 코드를 아는 쪽이 판단한다.** 후자면 이 단계는 없애는 게 원칙에 맞다.

다만 **표본이 아직 3건이다.** 지목만으로 사례를 뽑을지, 적발률·발언 길이 같은
A층 신호를 같이 볼지는 데이터가 더 쌓여야 판단이 선다. 첫 사이클은 사람이
고르고, 지목이 충분히 모이면 그때 자동화를 검토하는 순서가 안전하다.

```
누군가 함정 문항을 찍었다  +  그 사람이 특정 발언을 지목했다
              ↓
      정확히 그 발언이 실패 사례
              ↓
      replay.ts 의 새 Case 로 들어간다
```

함정이 *"문제가 남았다"* 를, 발언 지목이 *"어디서"* 를, replay 가 *"몇 번이나"* 를
맡는다. 고리는 여기서 닫힌다.

## §9. SHA 만으로는 "같은 봇" 을 못 가른다

트리거 판정에서 가장 틀리기 쉬운 지점이라 따로 적는다.

`/x/provider`(`bot/admin-route.ts`)는 **재배포 없이** 봇 프로바이더를 바꾼다.
배포된 서버엔 터미널이 없어서 만든 숨은 주소인데, 그 결과 이런 판이 생긴다.

```
같은 커밋 SHA
  ├ qwen3.8-max 로 3판
  └ GPT-5.6 Sol 로 2판      ← 코드는 한 줄도 안 바뀜
```

**SHA 로만 세면 "같은 봇 5판"으로 집계된다.** 실제로는 다른 봇 둘을 섞은 것이다.
모델이 다르면 행동도 다르다는 것은 PR #34 에서 실측했다 — 같은 프롬프트로
`question` 한 자리가 qwen 2/8, GPT 8/8(전부 회피)로 갈렸다.

그래서 `games` 에 셋이 함께 남는다.

```
bot_commit_sha    프롬프트·로직을 고친 것을 잡는다   ← 자가개선이 바꾸는 것
bot_provider      사람이 손으로 바꾼 것을 잡는다
bot_model         같은 provider 여도 모델이 다를 수 있다 (GPT_MODEL 교체)
```

**같은 봇 = 셋이 전부 같다.**

### 값이 비어 있는 경우

```
bot_commit_sha = null      로컬 실행. Railway 가 주입하는 값이라 없다
bot_model = "(안 정해짐)"   그 환경의 .env 에 BOT_MODEL 이 없었다
```

둘 다 **의도된 동작이다.** 없는 값을 `'local'` 같은 문자열로 채우면 여러 번의
로컬 테스트가 "같은 봇"으로 뭉쳐 5판 판정에 잘못 끼어든다. **비어 있으면
집계 대상이 아니라는 뜻으로 읽으면 된다.**

2026-08-26 기준 종료된 판은 대부분 `sha=null` 이다 — 로컬에서 돌린 것들이라
그렇다. **배포된 서버에서 도는 판부터 집계에 잡힌다.**

## §10. 미해결 — 트리거가 개수만 세면 안 되는 이유

**전제 하나를 깔아야 한다. `Stop` 훅은 세션당 한 번이 아니라 정현이 말을 한 마디
할 때마다 돈다** (§4). 즉 "돌릴 때가 됐나?" 라는 질문이 하루에 수십 번 던져진다.

그런데 **개수를 세는 조건은 물어볼 때마다 똑같은 답을 준다.** 여기서 세 가지가 샌다.

### 샘 1 — `>= 5` 는 위로 샌다

```
19:00   5번째 판 끝남                     판 5개
19:05   클로드 코드 켜고 한 마디            훅 → 5개 이상 → PR 열림    ✅
19:06   "아 그리고 이것도"                 훅 → 5개 이상 → PR 또       ❌
19:07   또 한 마디                        훅 → 5개 이상 → 또           ❌
```

판이 한 개도 안 늘었는데 조건이 계속 참이다.

### 샘 2 — `== 5` 로 좁히면 아래로 샌다

```
19:00   5번째 판 끝남                     판 5개
        (그날 아무도 클로드 코드를 안 켬)
21:00   6번째 판 끝남                     판 6개
21:30   클로드 코드 켬                     훅 → 5개 아님 → 영영 안 돎   ❌
```

게다가 19:05~19:07 의 중복도 여전히 안 막는다 (개수가 5 로 고정이므로).

### 샘 3 — 머지 직후, "지금 봇" 이 옛 봇으로 읽힌다

"지금 봇" 을 로컬 `git rev-parse HEAD` + 로컬 `.bot-provider` 로 잡으면 안 된다.
로컬은 배포본보다 앞서 있고 `.bot-provider` 도 서버 것이 아니라 **0판으로 나온다.**
그래서 **DB 의 마지막 판에 찍힌 `(sha, provider, model)`** 을 쓴다 (§9).

다만 그건 정확히 말하면 *"지금 배포된 봇"* 이 아니라 **"마지막으로 게임한 봇"** 이다.
평소엔 같지만 한 순간 갈라진다.

```
월 14:00   PR 머지 → Railway 재배포 완료 → 새 봇이 서버에 올라감
           그런데 아직 아무도 플레이를 안 했다

월 14:30   훅이 돈다
           DB 마지막 판 = 일요일 판 = 옛 SHA
           → "지금 봇 = 옛 봇" 으로 판단 → 옛 봇 판 5개 → PR 또 열림   ❌
```

이 순간 PR 은 **이미 닫혀 있다**(머지했으니까). 그래서
*"열린 `/selfrefine` PR 이 있으면 안 돈다"* 는 검사에 안 걸린다. 그 검사는 샘 1 만 막는다.

### 셋 다 같은 구멍이다

전부 **루프가 "이 판들 이미 써먹었다" 를 기억 못 해서** 생긴다. 기억이 생기면 동시에 닫힌다.

```
훅이 100번 물어봐도   한 번 쓴 판은 소진 → 안 쓴 판 0개 → 조용히 끝남
판이 6개 7개 쌓여도   "안 쓴 판" 기준이라 안 놓침
머지 직후에 물어봐도   그 5판은 이미 소진 → 조용히 끝남
```

`stop_hook_active`(§4)는 이걸 대신하지 못한다. 그건 **한 답변 안에서** 두 번 도는
것만 막고, 다음 세션에선 `false` 로 돌아온다.

### 그래서 트리거 문구

```
전    지금 봇으로 끝난 판이 5개 이상인가

후    아직 한 번도 안 써먹은, 같은 봇이 돌린 판이 5개 이상 모였나
      + 돌고 나면 그 판들에 "썼다" 표시를 남긴다
```

`5개 이상` 은 그대로 둬도 된다. 뒤에 표시를 남기므로 위로 새지 않는다.
사람이 PR 을 급히 머지할 필요도 없어진다.

### 표시를 어디에 남길지는 봇 코드를 아는 쪽이 정한다

다만 성질 하나는 짚어둘 만하다 — **그 기록이 PR 에 같이 실려 머지되면 머지 자체가
소진 처리가 된다.** 사람 손이 하나도 안 들어가서 §0-1 원칙과 맞는다.

열린 질문
```
· 소진 단위가 판(id) 인가, 시각인가
· 사람이 PR 을 닫아버렸을 때(= 수정을 기각) 그 판들은 소진인가 아닌가
· sha 가 null 인 판(현재 42판 전부, 전부 로컬)은 아예 대상에서 빼는가
```
